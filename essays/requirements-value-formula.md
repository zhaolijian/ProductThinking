# 用户说「想要一个 XX」，产品经理该怎么翻译成需求？

2026-11 · 约 1800 字

面试里最容易被问倒的一题是「你怎么做需求分析」。我早期的回答是背流程：收集需求、分析需求、排优先级、写 PRD。后来发现这套回答有个明显的问题——它解释不了，为什么大部分需求最后都该被砍掉。

现在我更愿意从一个具体的用户原话讲起。产品经理真正的手艺，是把用户嘴里的「解决方案」还原成「问题」，再决定要不要做。

## 用户说的「XX」，是解决方案，不是问题

做阅记时，在用户沟通里最常听到的一句话是：「我想要一个能拍照记笔记的 App。」

如果直接接需求，路线很清楚：做拍照入口、接 OCR、识别结果存进列表、加导出，一个 MVP 就出来了。但我多问了自己一句：他要的是「拍照」，还是「把书里的划线句留下来」？

往下拆了三层才看到真问题：手抄太慢所以想拍照；拍完的笔记要用来复习、找依据；现在大多数人的做法是相册加备忘录，或者干脆不整理。也就是说，用户缺的不是记录动作，而是**把划线句变成能复习的结构**——录入成本高、结构缺失、无法迁移，三个断点。

产品最后长成了「拍照识别 → 按章节定位 → 结构化整理 → 生成思维导图 → 导出到已有笔记软件」，和「一个拍照记笔记的 App」已经不是同一件事。如果按用户的原话做，我能做出一个能用的工具，但大概率没人会天天用。

我后来把这件事固化成一句翻译公式：**场景 + 现有替代方案 + 缺口 + 期望结果**。用户能提供前两项，产品经理负责后两项。当用户说「想要一个 XX」时，他其实已经替你选好了解决方案，这才是最该警惕的一刻。

落到动作上，我用的顺序是四步：

1. **听：先收原话，尤其要收「他现在怎么凑合」。** 替代方案比痛点有信息量——用户能忍受的现状，决定了你的产品要跨过多高的门槛。
2. **拆：5 Why 与 JTBD 交替问。** 不要问「你需要什么功能」，要问「上一次发生这件事是什么时候、你当时做了什么、结果怎样」。
3. **选：用「价值 × 频次 × 可行性」筛一遍。** 三格都不占的直接丢。这一步最考验敢不敢砍。
4. **定：写成可验收的 PRD。** 用户故事、验收标准、边界条件、指标，四样缺一不可。

这四步里，看起来最专业的是「拆」，最有产出感的是「定」，但决定成败的往往是「听」和「选」：听的时候有没有拿到替代方案，选的时候敢不敢把伪需求丢掉。

## 用户价值是一道减法题

俞军给过一个公式：用户价值 = 新体验 − 旧体验 − 替换成本。这个公式我越用越觉得解释力强，因为它逼你承认两件产品经理经常假装看不见的事：用户有旧方案，换你有成本。

> 大部分产品只优化「新体验」，然后困惑用户为什么不换。问题往往不在新体验不够好，而在旧体验没那么差、替换成本又很高。

阅记就是现成的例子。新体验确实比「相册 + 备忘录」好，但旧体验并不差——Notion、飞书、印象笔记已经能记笔记、能检索、能同步；替换成本还很高——已有笔记要迁、习惯要改、要学一个新工具。三项相减，价值可能接近零，甚至为负。这解释了为什么「功能更好」不等于「用户会换」。

要让用户价值为正，只有三条路，每条都是取舍：

- **新体验领先一个数量级**：不是好 20%，而是「原来做不到的事现在能做到」。领先幅度不够，用户根本感知不到。
- **把替换成本压到接近零**：支持导入导出、和用户已有的工具共存，而不是要求他取代旧工具。降低门槛本身就是在创造价值。
- **换一个旧体验足够差的场景**：老办法是纸笔、Excel、人肉流程，而不是成熟软件。旧体验越差，减法越容易为正。

商业侧同理：商业价值 = 愿付价格 − 企业成本。两个公式同时为正，需求才真的成立。很多需求被砍，不是用户不需要，而是企业算不过账——获客太贵、交付太重、复购太低。

## KANO、价值成本矩阵、RICE：不是三选一

这三个模型最大的问题不是不好用，是被当成「高级需求分析」到处套。我的用法是先看场景，再看模型：

| 模型 | 什么时候用 | 判断标准 | 风险 |
| --- | --- | --- | --- |
| **KANO** | 0→1 阶段，需求还没被验证 | 没有它，用户会不会直接走？先补齐基本型，别一上来做兴奋型 | 分类来自用户主观回答，样本小的时候容易把「想要」当「必须有」 |
| **价值 × 成本矩阵** | 存量优化，资源有限，单个决策争议大 | 只回答两个问题：给用户多少价值、实现与维护成本多高 | 「高价值高成本」的象限靠表格决定不了，得靠战略判断 |
| **RICE** | 向上沟通、跨团队排序、需要解释资源分配 | 四个输入里至少一个要有真实数据，否则只是给偏见披上量化外衣 | 参数靠拍脑袋时，结论比不用模型更危险 |

我自己的用法很朴素：一个人做产品时用矩阵，因为要排序的需求没那么多；需要说服别人时用 RICE，因为要给理由；0→1 阶段先用 KANO 过一遍「基本型」，把「用户会不会直接走」问清楚，再谈兴奋型。

一句话：模型的价值是逼你把「凭什么」说清楚，不是算出一个看起来精确的名次。

## 这套方法的边界

第一，公式给方向，不给权重。新体验、旧体验、替换成本都是主观量，没法精确打分。它的作用是让你承认「旧体验」和「替换成本」存在，而不是算出一个小数点。

第二，用户访谈不能替代行为证据。用户说的替代方案可能是美化过的，要看他上次整理笔记是什么时候、导出了哪个文件、有没有真的付费。

第三，B 端不能直接套 C 端公式。B 端的替换成本常常是组织成本：权限要重配、流程要改、要培训、要过合规。我在中台做 SDK 和 Web 平台两端时体会最深——能力再强，业务方不会用、不敢用，价值就是零。C 端的「体验更好」在 B 端经常不是决策理由。

第四，用户价值为正不等于值得做。商业价值为负、或者你根本触达不到用户，需求成立也做不成产品。
